Mumblew — Phase 13.5 benchmark round 3 (dual-worker parallelism)

Rounds 1/2 (Entry 35-37) established a single-Kokoro-instance throughput ceiling that no buffer depth could fix. This round tests the "dual-oven" idea: spawn a second independent worker, each holding its own Kokoro instance, and round-robin sentences across the two — see whether the hardware has room for real parallel synthesis, or whether two instances just contend for the same GPU/CPU and cancel the gain out. Panels 1-3 are unchanged from round 2 (still useful for single-worker comparison numbers); panel 4 below is the new dual-worker test. Fully isolated — doesn't touch main.js/index.html.

Run this via a local static server (e.g. npx serve or python3 -m http.server), not by double-clicking the file — the worker's import needs a real origin. Also don't deploy this through Vercel as-is: the current vercel.json CSP doesn't allow the Hugging Face model-file domains Kokoro downloads from, it would just get blocked.

dtype auto-suggests fp32 for webgpu, q8 for wasm (Kokoro's own recommendation) — override if you want to compare.

2. Reader pace

Phase 11 calibrates baseWordMs/msPerSyllable per person — the earlier flat "400ms/word" guess in this harness was replaced with the app's real per-word formula (baseWordMs + syllables × msPerSyllable), so different readers can actually be tested instead of assumed. Pick a preset or type your own — this is exactly what a fast vs. slow mumbler comparison needs.


3. Tests


Depth only changes how far ahead the queue is allowed to run — there's still only one Kokoro instance in the worker, so requests are dispatched to it one at a time regardless of depth. Deeper buffering can absorb bursts/variance and hide sentence-0-style cold starts further into the run, but it can't fix a sustained case where synth time > read time per sentence — that's a throughput ceiling, not a buffering problem, and the summary below calls it out explicitly if so.


Raw latency: how long tts.generate() takes per sentence, sequential, no overlap — directly comparable to Entry 35's 9–18s/sentence numbers.
Pipeline test: simulates real reading — synthesizes sentence N+1 in the background while "reading" sentence N (estimated ms/word), then reports the perceived wait, which is what a reader would actually feel.
Streaming test: uses Kokoro's tts.stream() API instead of generate() on a multi-sentence paragraph — tests whether the first audio chunk arrives faster than a full generate() call finishes, which would matter more than total synthesis time.
Concurrent test: same pipeline test, but with MediaPipe's face landmarker running live via your webcam the whole time (fps shown below). The delegate dropdown lets you test GPU (what main.js currently uses) vs CPU — this checks whether WebGPU-Kokoro and GPU-MediaPipe are contending for the same hardware.

4. Dual-worker parallelism test (new, round 3)

Spawns a second independent worker, each holding its own Kokoro instance, and round-robins sentences between them — sentence N+1 synthesizes on worker B while sentence N is still finishing on worker A, instead of queuing behind it in one worker. Uses the device/dtype from panel 1 (same backend in both workers, so this isolates "does 2x concurrent instances help" from "which backend is faster"). Loading a second instance roughly doubles VRAM/RAM for model weights — a load failure or degraded FPS on the concurrent variant is real data, not a bug to fix.

Dual-worker test: same simulated-reading pipeline as panel 3's test, just dispatched across 2 workers instead of 1.
Comparison: runs the equivalent single-worker pipeline, then the dual-worker one, back to back at the same depth/pace, and prints the speedup directly — this is the number that actually answers the question. Use this one first.
